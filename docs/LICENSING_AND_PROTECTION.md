# 离线许可与保护：设计判定记录

本文件记录一次关于「客户端保护」方案讨论的结论，供 NUT 与 NU 复用。
它讨论的是**该不该做、能做到什么上限**，不是某个具体实现。

状态：结论性记录，非实施计划。

---

## 1. 一句话结论

**客户端能做的只有「许可（licensing）」，做不了「保护（protection）。」**
两者常被混为一谈，但上限完全不同：

| | 目标 | 在纯客户端能否达成 |
|---|---|---|
| 许可 | 让未授权者**不能合法使用**；设备绑定、到期、防随意外传 | **能**，配合承重式派生可到"没有授权材料就用不了功能" |
| 保护 | 让有决心的攻击者**无法使用/无法逆向** | **不能**。等价于在一台完全由攻击者控制的机器上执行"不许运行"的判决 |

判定一个方案属于哪一类，只需问一句：**验证方在哪？**
如果验证方和"被保护的东西"跑在同一台攻击者的机器上，那就一定是许可，不是保护。

---

## 2. 承重式派生：唯一真正有价值的一环

普通的门禁是一个布尔判断：

```
if license_ok: run()   ← 攻击者把这一行 nop 掉即可
```

**承重式派生**把它变成密钥问题：

```
license → (派生) → 解锁密钥 → 解开受保护资源
没有合法 license → 派生不出密钥 → 资源永远是密文
```

这样"绕过判断"不再等于"能用功能"，因为**你手里没有那把钥匙**。
这是许可方案里唯一值得投入的部分，其余（界面、提示、时间戳展示）都是装饰。

### 它的两条硬边界

1. **必须是"每次授权唯一"的密钥材料参与派生。** 若所有人都派生同一把主密钥
   （因为大家解同一批 payload），那么**任何一个合法持有者提取一次就能永久分享**。
   要堵，只能按 license 重新加密资源（对 MB 级 payload 不现实），或按次下发
   （那就退回在线了）。
2. **明文最终必须在端点上出现。** 资源要能用就得解密，解密的那一瞬间明文在内存里。
   派生只是抬高门槛，不改变这个事实。

## 3. 离线为什么防不住：三个条件同时成立

离线 + 共享资源 + 本地输入 —— 三者同时成立时，**没有密码学方案能救**：

| 条件 | 为什么致命 |
|---|---|
| **本地输入** | 秘密（密码/口令）必须以明文形式在端点上存在过。系统级输入采集（键盘记录、输入路径 hook）或输入瞬间的内存 dump 都能拿到。**KDF 再强也不改变"秘密出现在端点"这个事实。** |
| **共享资源** | 同一批 payload 用同一把密钥，一个诚实持有者提取后即可全局分享。 |
| **离线** | 没有服务端在每次操作时重新裁决，授权状态一旦落到本地就固化了。 |

**这不是"密码学不够好"，是这三条本身不允许。** 换更强的 KDF、换更长的密钥、
加内存清零，全都不改变结论。

### 与 xingc（vivo）的对比——本方案的灵感来源

| | xingc / vivo | 客户端许可门禁 |
|---|---|---|
| 签名者 | 主机（私钥） | 授权程序（私钥） |
| **验证者** | **设备 secboot / OTP 固化的公钥** | **PC 上那个二进制里的一段字节** |
| 攻击者能改验证者吗 | 不能（硬件熔断） | **能，改几个字节** |

xingc 成立的全部原因，是**验证方在攻击者碰不到的地方**。
一旦把验证方搬到攻击者的机器上（哪怕逻辑一模一样），强度就塌了——
攻击者把自己的公钥写进去，然后自己签自己，永久通过。

**结论：可以借鉴 xingc 的"挑战—应答—签名"形状，但不能假设有同级的安全性。**
缺少硬件根，形状的相似没有意义。

## 4. 信任层级

| 层级 | 信任根 | 被什么打破 | 成本 |
|---|---|---|---|
| 离线 + 本地密码 | 用户的记忆 | 输入采集 / 内存 dump | **极低（装个键盘记录器）** |
| 离线 + 承重派生 | 私钥持有者 | 同上 + 一个诚实持有者分享 | 低到中 |
| 在线 + 一次性授权 | 服务端 + TLS + 单次票据 | 端点动态逆向（调试器/hypervisor/hook 解密点） | **中到高** |
| 硬件（secboot / TPM / OTP） | 芯片 | 物理攻击 / 故障注入 | 高 |

**每一层的实际价值是"抬高攻击成本"，不是"杜绝"。** 选择哪一层，取决于威胁模型：
防随意外传 vs 防专门逆向，是完全不同的预算级别。

## 5. 在线设计为什么强（以及不是"无解"）

在线方案（NU 的方向）的核心：**密钥材料从不在端点上持久存在**，
而是按操作下发一次性授权，用完即弃。

它挡住的是**杀死离线方案的那一类攻击**：静态分析、键盘记录、离线解密。
因为端点根本没有可解的密码或可提取的长期密钥。

残留路径（确实存在，但贵得多）：

- **瞬时 dump**：CEK 下发的瞬间必须在进程内存里存在，内核调试器 / hypervisor 可捕获；
- **hook 解密点**：直接拦到解密调用，绕过验证。

关键是**成本不对称**：离线被打穿的技能门槛是 0，在线需要专门的动态逆向能力
且要卡准时机。对"防止随意外传"这个现实威胁模型，在线方案**事实上不可破**。

补充：这也是为什么把密钥相关逻辑收进**独立的小进程**（NU 的 Device Host /
Security Cell 拆分）有意义——把明文的生存窗口压到最小、最可审计的边界内，
而不是让它躺在一个巨大的主进程里被一次 dump 全部带走。

## 6. 若仍要实施：最小正确方案

如果目标明确是「许可」（防外传 / 到期 / 设备绑定），最简构成即可，
**不要过度设计**：

```
客户端  → 请求文件 { 设备指纹, 时间戳, nonce }
授权侧  → license 文件 { 设备指纹, 时间戳, 到期, 签名 }
客户端  → 用内嵌公钥验签；指纹比对；now < 到期
```

要点与常见错误：

- **不需要双重加密。** 请求侧不含秘密，无需公钥加密；响应侧**只需要签名**，
  不要用"私钥加密"这种说法（RSA 下数学等价，但请明确走签名语义，避免填充误用）。
- **优先用 Ed25519**（32 字节签名、无填充陷阱），而不是 RSA-2048。
- **指纹**优先用 TPM 支持的不可导出 CNG 密钥公钥；MAC/磁盘序列号弱且会随
  硬件变更或重装而变。
- **时钟可回拨。** 本地时间不可信，若要检测需持久化"上次见到的时间"并做防篡改，
  但那也在客户端，属于"抬高成本"而非"杜绝"。
- **让 license 参与上一节的派生**，否则它只是一个能被 nop 的分支。

## 7. 判定清单

拿到任何新的客户端保护构想，按顺序问：

1. **验证方在哪？** 在被保护机器上 → 这是许可，不是保护。
2. **攻击者需要做什么才能绕过？** 如果答案是"改几个字节 / 改系统时间"，
   那它只是装饰。
3. **它承重吗？** license 是否参与解密密钥派生？如果是纯布尔判断，价值接近 0。
4. **一个诚实用户能否分享？** 如果所有用户共享同一把派生密钥，答案是"能"。
5. **成本是否匹配威胁模型？** 防外传就别上重型混淆；防专门逆向就别指望纯软件。
6. **它会不会伤稳定性？** 授权逻辑出问题会变成"正版用户用不了"，
   对"简单/稳定"优先的产品是净负收益。

## 8. 本项目的具体结论（NUT）

- 离线产品的**逻辑已经完整公开**（含系统级输入采集获取的口令）。
  在"已经公开"的前提下，**任何保护投入的边际收益都接近零**——
  攻击者手里已经有钥匙和图纸。
- 因此本产品的定位应是**"简单、稳定的工具"**，而不是"需要守住的资产"。
  VMProtect 之类的投入在这一前提下不成立（且只保护 EntryPoint 更是象征性的），
  这也是开源版直接删掉访问密码门禁与壳的原因：留着只会伤害稳定性与可维护性。
- 要投入保护，**只投全新的、尚未泄漏的东西**；
  并且优先投在**在线形态**（服务端持有材料）或**硬件根**（TPM/secboot）上，
  而不是客户端软件混淆。
